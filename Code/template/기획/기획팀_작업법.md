# 기획팀 작업법

> 라이선스: 이 문서만 CC BY-NC-SA 4.0 (https://creativecommons.org/licenses/by-nc-sa/4.0/) — 앱 코드와 별개이며, 아래 원문에서 고쳐 옮긴 것입니다. 다시 나눌 때도 같은 조건(출처 표시·비영리·같은 라이선스)을 따라 주세요.
> 출처: 『현업 게임 기획자의 Claude Code 활용서』 (eremes81, github.com/eremes81/game-design-ai-practice, CC BY-NC-SA 4.0) 중 우리 규모에 맞는 것만 골라 우리 말로 옮김.
> 절차로 굳히지 않는다 — 아래는 "이럴 땐 이걸 본다" 이지 매번 도는 단계가 아니다.
> **이 파일은 앱이 들고 있다** — 앱을 켤 때마다 모든 프로젝트에 새 판으로 덮인다. 여기를 고치지 말고, 게임별로 정한 것은 `결정_기록.md`·`밸런스.md`·`숫자_지도.md` 에 적는다.

## 1. 시그니처 한 줄을 먼저 지킨다 (책 23.4)
- 참고 게임을 요약해서 옮기면 그 게임만의 손맛이 사라진다. 저자의 첫 버전이 "실 풀기 퍼즐"을 "흔한 분류 퍼즐"로 납작하게 만든 사례.
- 우리 시그니처 = `게임컨셉.md` "시그니처 한 줄" (사장님 확정 전은 가안). (예: 카드 게임이라면 "순서 퍼즐" 같은 한 줄)
- 새 시스템·카드·화면이 들어올 때 묻는다: 시그니처를 살리나, 가리나? 가리면 숨기거나(화면에서 숫자 빼기) 빼자고 제안한다.
- 결과가 이상하면 코드가 아니라 **정의(기획 문장)부터 고친다**.

## 2. "무엇이 아닌가" 에 걸리면 멈춘다 (책 19.1)
- 위반은 "하기로 한 것"보다 "안 하기로 한 것을 슬그머니 하는" 자리에서 나온다.
- `게임컨셉.md` 비전 5칸의 5번에 걸리는 아이디어는 만들기 전에 사장님께 한 줄로 여쭌다 (그 외는 D15 "일 좀 하자" 대로 바로 만든다 — 단 새 시스템은 8절 관문 뒤).

## 3. 사장님 결정은 `결정_기록.md` 에 한 줄 (책 19.1·19.3)
- 날짜·결정·사장님 말·영향 파일. 뒤집혀도 지우지 않고 "→ 대체" 를 붙인다.
- 기록 안 된 결정은 나중에 "그런 말 한 적 있나?"로 흐른다.

## 4. 숫자는 시뮬로 바꾼다 (책 8.1·8.4)
- 숫자 변경 = 후보 → 같은 시드로 전후 시뮬 → 고르기 → `밸런스.md` 변경 이력 한 줄.
- AI(Claude)는 후보와 해석까지. "원인은 X" 라고 단정하지 말고 가설 몇 개와 각각 확인할 시뮬 한 줄을 낸다.
- 시뮬 숫자는 봇 기준. 사람 체감은 사장님 플레이로만 안다 — 둘을 섞어 말하지 않는다.

## 5. 데이터를 고치면 검사부터 (책 3.2·10.1)
- 게임 데이터(카드·아이템·스킬 등)를 고치면 데이터 검사 스크립트(`tests/` 아래, 없으면 만들자)부터 돌린다: id 중복 → 참조 → 범위 → 그림·설명. P0 = 게임이 깨짐, P1 = 확인할 것.
- 거짓 경고가 나오면 검사 코드의 ALLOW 에 이유 한 줄과 함께 넣는다. (예: 카드 게임이라면 `tests/check_cards.gd`)

## 6. 늘리기 전에 빼기를 같이 본다 (책 21.3·23.3)
- 시스템은 막지 않으면 늘어난다.
- 새 시스템을 제안할 때: 기존 것을 키워서 되나? 안 되면 무엇을 숨기거나 뺄지 같이 낸다.
- "한 턴에 따질 게 많다" 싶으면 이 원칙으로 푼다 — 시그니처가 정해지면 그쪽이 아닌 것부터 화면에서 숨긴다.

## 7. AI 산출물엔 자기 신고 칸 (책 22.1)
- 기획안·데이터·시뮬 해석 끝에 "확신 없는 곳" 을 ★ 로 적는다. 사장님은 ★ 만 보면 된다.

## 8. 재미 판정 없이 늘리지 않는다 (FF14 신생에서)
- 출처: 요시다 나오키 GDC 2014 — 신생 FF14 는 기본 설계 약 400개가 확정되기 전엔 프로그래머에게 "코드를 쓰지 마라". 1.0 은 화분 하나에 캐릭터만큼 폴리곤·셰이더를 써서 화면 인원을 20명으로 묶었다(그림이 게임 체험을 깎음).
- 예(어느 카드 게임): 첫 관문은 "순서 퍼즐이 재밌나" 였는데 판정 기록 없이 시스템과 그림이 얹혔다.
- 규칙: **새 시스템을 넣기 전에** 사장님 5분 한 판(스테이지 1) 판정이 `QA/현황.md` "재미 판정" 에 있어야 한다 — "재밌나 Y/N + 한 줄". 시그니처(`게임컨셉.md`)가 확정 전이면 "어느 쪽이 재밌었나" 한 마디도 받는다 — 판정이 시그니처를 미리 정하지 않게, 오히려 고르는 재료로.
- 새 시스템 = 판에 **새 규칙·새 자원·새 상태**를 더하는 것 (예: 새 화폐, 새 단계, 새 상태이상). 기존 규칙 안에서 도는 새 카드·몬스터·대사 같은 것은 콘텐츠라 막지 않는다.
- 막지 않는 것: 콘텐츠, 그림·사운드, 버그 수정, 숫자 조정(스테이지 난이도 포함), 기존 시스템 다듬기·숨기기, 시뮬·점검 도구. D15 "일 좀 하자"(묻지 말고 만들기)는 그대로 — 이 관문은 묻는 게 아니라 판정 한 줄을 기다리는 것.
- 판정 N 이면 정의(기획 문장)·숫자부터 고치고 **다시 한 판** — Y 가 나와야 새 시스템이 풀린다. Y 뒤에 새 시스템을 넣었으면 그다음 새 시스템 전에 다시 판정 (한 번의 Y 로 계속 늘리지 않음).

## 9. 문제가 먼저, 해법은 나중 (Iwata Asks 를 읽고 우리가 한 실수에서)
- 책·강연에서 멋진 해법을 읽고 "우리 게임 어디에 넣을까"부터 찾지 않는다. 먼저 있는 것 = 사장님 불만, 플레이 판정, 시뮬 숫자. 그 문제에 맞는 해법을 찾는다.
- 예: 젤다 Z주목의 "적은 한 번에 하나씩 덤비고 나머지는 기다린다"를 읽고 몬스터 공격 순번 설계까지 썼지만, "몰려 맞아 억울하다"는 판정이 한 번도 없었다 → 가능성 ≠ 문제. 설계안은 보관만.
- 규칙: 새 장치를 제안할 땐 첫 줄에 "이걸로 푸는 문제 = (판정·숫자·불만 원문)". 그 칸이 비면 제안하지 않는다.

## 10. 길 안내는 화살표보다 배치로 (젤다 야숨 CEDEC 2017 강연 요약에서, 검증 안 됨)
- 문제였던 것: 탑을 퍼뜨리고 사이에 이벤트를 두자 플레이어가 "끌려다닌다·너무 일자형이다"라고 느꼈다.
- 해법: 삼각형 지형을 세 크기로 — 큰 것 = 멀리서 보이는 목표, 중간 것 = 시야를 가려 넘어가 보고 싶게, 작은 것 = 걷는 리듬. 넘을지 돌지 고르게 하고, 가린 뒤에 다음 관심거리를 둔다 (언덕 → 다리 → 탑, "관심의 사슬").
- 검증 방법이 더 중요: 바꾸기 전·후 이동 경로 히트맵을 비교했다. 우리도 맵·스테이지를 고치면 "어디로 갔나"를 기록해 전후로 본다 (작은 게임이면 플레이 로그 몇 판).
- 맵이 없는 게임(카드·퍼즐)에선 "다음에 볼 것이 살짝 가려져 있다"로 옮긴다 — 다음 스테이지 보스 실루엣, 잠긴 카드 칸 같은 것.

## 11. 그림·연출 비용은 게임 체험이 정한다 (FF14 1.0)
- 화분 하나가 캐릭터만큼 무거워서 한 화면에 20명밖에 못 보여 준 것처럼, 그림 욕심이 게임의 핵심(사람 많은 MMO)을 깎을 수 있다.
- 규칙: 기획 문서에 "이 게임에서 한 화면에 동시에 보여야 하는 것"(카드 수·적 수·이펙트 수)을 먼저 적고, 리소스팀 그림 규격은 그 숫자에서 나온다.

## 12. 결정 안 된 것을 문구로 몰래 정하지 않는다
- 판정 질문·체크리스트·관문 문장을 쓸 때, 아직 사장님이 안 정한 것(예: 시그니처 A안/B안)을 질문이 한쪽으로 미리 가정하지 않는지 본다. 가정하면 "A/B 중 어느 쪽이 재밌었나"처럼 고르는 재료가 되게 바꾼다.

## 13. 실험은 대조군부터
- "이 방법이 낫다"를 보려면 안 바꾼 판(대조군)을 같은 조건으로 먼저 만든다. 대조군 없는 결과는 읽을 수 없다. 시간 상한·멈출 조건도 시작 전에 적는다.

## 14. 숫자 지도 — 숫자가 어디 살고 무엇을 나타내나 (Game Balance Concepts L1, Ian Schreiber 2010)
- 책: 밸런스는 대개 게임에 쓸 숫자를 정하는 일이고, 눈에 안 띄는 숨은 숫자도 게임 상태를 기술한다. 게임이 맞아도 고르는 판(메타게임)이 기울면 밸런스가 무너진다.
- 시스템이 서너 개 붙으면 `기획/숫자_지도.md` 를 한 번 만든다: ① 이 게임의 상태 덩어리(체력·자원·진행 등)와 각각의 수입·지출 ② 숫자가 사는 곳 — 숫자 표(시뮬로 덮어쓸 수 있나) / 코드 속 맨숫자(숨은 숫자) / 화면 설명 글자 ③ 판에 영향 큰 숨은 숫자 목록. 값은 옮겨 적지 않는다 (원본 = 코드, 이력 = `밸런스.md`).
- 같이 찾는 것: 안 쓰이는 숫자(시뮬로 바꿔도 결과가 그대로 = 죽은 숫자, 바꿔 보는 사람을 속인다), 같은 숫자가 두 곳(컨셉 문서·설명 글자·코드)에 따로 적힌 것, 시뮬로 못 건드리는 숫자.
- 메타: 플레이어가 고르는 것(무기·직업·장비)이 한쪽으로 몰리는지 — 봇 수치와 사람 판 "누가 뭘 골랐나" 를 따로 본다.

## 안 가져온 것 (규모가 안 맞음)
- 엑셀·스키마 문서 생성기, 협업툴 알림, 슬래시 명령 묶음, 메모리 자동 주입, 라이브 서비스 사후 측정, 자원별 경제 시뮬 도구.
